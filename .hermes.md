# hermes-host-bootstrap — project context for Hermes

This repository defines fleet-wide shell aliases, helper scripts, bootstrap
modules, and host conventions. Changes here propagate to every fleet host, so
they have a documentation obligation that is easy to forget.

## Definition of done for changes in this repo

A change to an alias, helper script, bootstrap module, or host convention is
NOT complete until all three layers are updated:

1. **Source** — `dotfiles/aliases.sh`, the helper script under `scripts/`, and
   the registration/install module under `lib/` (e.g. `99-register-host.sh`,
   `30-shell.sh`). Commit + push.
2. **Wiki source** — load the `hermes-automation-wiki` skill and update the
   relevant Markdown page(s). New/changed commands and aliases go in
   `operations/handy-commands-and-aliases.md`; terminal/tmux/mouse behavior in
   `operations/terminal-state-reset.md`. Add a `log.md` entry.
3. **Published HTML** — run the wiki's `scripts/publish.py` +
   `scripts/build-mkdocs.py`, sync to the served dir, and verify HTTP 200.

This is the "documentation loop" that the wiki skill's maintenance rule
prescribes. Treat it as part of finishing the task, not a follow-up.

## Why this file exists

The wiki-update step is cross-cutting: it applies to any command/alias/script
change regardless of which topic-skill you loaded to make the change. Hermes
surfaces topic-skills by relevance (LLM judgment over the `<available_skills>`
menu), so a documentation rule buried inside one topic-skill is unreachable
from sibling tasks. Project context files like this one are injected
deterministically for every session under this repo's git tree, so the rule
fires no matter what you came here to do.
